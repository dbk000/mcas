## Observations / surprises

- **No fakeredis in base venv.** Installed via `pip install --break-system-packages --user fakeredis` (Python 3.12 PEP 668 enforcement). Already widely available in the worker container's image — assumed present at deploy time; if not, add `fakeredis` to `Backend/requirements-dev.txt` (test-only dep).
- **`Backend/workers/` did not previously exist.** Existing background workers live under `Backend/governance/` (signal_worker, indicator_worker, ingestor, etc.). Created a new top-level `workers/` package per the plan's path spec; this matches the §Phase A file list exactly and avoids polluting `governance/` with a temporary detector.
- **Plan §Phase A spec said "drawdown ≤ -3%"** but elsewhere (§2 Phase A line 73) said "BTC 4h drawdown ≥ 2%". Used **-3%** as canonical (matches the brief in this task) — exposed as `REGIME_DETECTOR_BTC_DRAWDOWN` env var so deploy operator can flip without code change.
- **`governance/persistence.get_conn()` is the established pool pattern.** `regime_detector._build_enforcer_and_conn()` follows it. The detector receives `pg_get_conn` as a callable arg so tests can inject mocks; module-level wiring only happens in `main()`.
- **`enforcer.set_state` audit-write behaviour is best-effort.** A failed audit insert logs and continues — does NOT roll back the Redis state flip. Rationale: in a SHOCK, getting the Redis key set is more important than getting the audit row. Operators inspect Redis (live) and `enforcer_events` (post-mortem); the live signal is the load-bearing one.
