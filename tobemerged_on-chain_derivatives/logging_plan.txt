1. Current Logging Capabilities for Strategy Analysis

Structured Logging Infrastructure: The MCAS system already emits detailed, structured logs in JSON format for both real-time events and persistent records. A custom JSON logger attaches contextual identifiers (like run_id, worker_id, symbol) to every log entry. This means that when a backtest or paper-trade run is executing, all log lines are tagged with that run’s ID for easy grouping. Key trading events are logged with informative fields: for example, when the worker opens or closes a position, the log includes the event type and relevant data (symbol, prices, P&L, etc.). For instance, upon a paper trade exit, the system logs a JSON line like:

{"event": "position_closed", "position_id": "...", "symbol": "...", "side": "...", 
 "exit_reason": "...", "exit_price": ..., "entry_price": ..., 
 "realized_pnl": ..., "gross_pnl": ..., "total_fees": ..., "r_multiple": ...,
 "run_id": "...", ...}


. This captures the outcome (profit/loss, R-multiple, fees) and context of each closed trade.

Logging of Inputs & Decisions: When a trading signal is generated, the system records its input features and decision context. In SignalEngine.evaluate_setups, every time a setup triggers, a SETUP_FIRED event is inserted into the signal_events table with a full snapshot of the indicators and conditions at that moment. For example, a trigger of setup “S1” logs fields like Bollinger Band width, percentile, squeeze duration, bias score, volume Z-score, ATR, etc., along with the setup’s score components and even the list of textual “reason codes” explaining the signal (e.g. “BB width at 20th percentile”, “Volume participation 50%”, etc.). This means all input variables and the rationale behind a signal are captured at the moment of decision.

When a trade is taken from a signal, it is persisted as a RunTrade record including the entry decision details. The code converts each signal into a trade object containing the asset, timeframe, side (long/short), entry/exit prices, stop loss, take-profit levels, etc., as well as an embedded trace of the decision context. Notably, the trace stores the conditions and indicators at entry (e.g. entry price, stop distance r_value, key indicator values) and a copy of the signal’s state and score components. For example, a trade trace might include a state_snapshot with the signal’s state (such as whether a squeeze was on, bias metrics, etc.) and the score_components that led to its ranking. The system also attaches the top reasons (why_items) for the trade entry into this trace. All of this is saved in the run_trades table as a JSON blob (trace_json) alongside the trade’s performance outcome. In summary, each trade record in the database contains the inputs (indicators, state) and decision rationale at entry, and the outcome at exit.

Logging of Outcomes: As trades progress, outcomes are logged both in real-time and in summary form. Every trade closure (whether hitting a stop, take-profit, or other exit) is recorded in the paper_positions/run_trades records with its exit reason and final P&L (including realized P&L and R-multiple). Simultaneously, an INFO log line is emitted for visibility, as shown above in the position_closed example. The system also tracks aggregate metrics in a RunSummary for each run – e.g. total trades, win rate, profit factor, max drawdown, etc. – which is stored and can be logged at run completion. For instance, after a backtest run, the code logs a summary event like “Backtest complete: 45 trades, 55.6% win rate, capital 10000 -> 10550, max DD 8.5%, 120 signals generated.”. This gives a high-level outcome overview for the run.

Assessment – Sufficient for Post-Mortem: Overall, the current logging captures all three phases – inputs, decisions, and outcomes – in a structured way. The combination of signal_events (for setup triggers with full context) and run_trades/paper_positions (for actual trades with context and results) provides a solid audit trail. A strategist can retrieve, for any given trade, exactly what the market state and strategy reasoning were at entry, and see how the trade concluded. This is a strong foundation for regression-based learning and post-mortem analysis.

However, a few minor gaps exist that we will address (e.g. ensuring some fields are consistently logged for easier analysis). Generally, the logging in place is quite rich and nearly sufficient – only a few enhancements are needed to make analysis even more effective.

2. Workflow to Leverage Logs for Iterative Strategy Improvement

With the logging infrastructure in place, the team can follow a structured feedback loop after each batch of trades (or simulation run) to drive regression-based learning:

a. Collect Data After Each Run: Upon completing a paper-trading session or backtest, gather the logged data for analysis. This typically involves querying the trade logs and signal logs from the database. For a given run, you’d pull all entries from run_trades (or paper_positions for live forward-testing) associated with that run ID, as well as relevant signal_events. Each trade record provides the trade’s outcome (win/loss, R-multiple, P&L) and the full set of input features and context at entry (from the trace_json). You might also retrieve the run’s summary metrics (win rate, net profit, etc.) as a starting point for evaluation.

b. Analyze Trade Outcomes vs. Inputs: Using this data, perform a post-mortem analysis to identify patterns. Key steps include:

Group and Filter: Separate trades by strategy setup (e.g. S1 vs S2) or by outcome (winning vs losing trades). This allows you to compute metrics per category – for example, win rate for S1 trades versus S2 trades, or average R-multiple for trades that triggered under certain conditions.

Feature Correlation: Treat each trade as a data point with features (the logged indicators/metrics at entry) and an outcome (e.g. profitable or not, or the R-multiple achieved). Perform regression analysis or even simple statistical checks to find which input features have predictive power for success. For instance, you may find that trades with very low “volume_z” or low “break_quality” scores tend to be losers. If the logs show a trade’s score components – e.g. participation, break_quality, trend_strength – you can plot those against the trade’s R-multiple to see if higher values correlate with better outcomes. This could be done via a logistic regression (win vs. loss) or linear regression (predicting R-multiple) on the logged data, hence “regression-based learning.”

Identify Weak Spots: Pay special attention to any common factors in losing trades. The rich context in trace_json (including reason codes and indicator snapshots) lets you answer questions like: “Are many losing trades characterized by a certain condition, such as a tight BB width percentile or a certain bias score?” or “Do signals with a particular why-item (reason code) often fail?” For example, you might discover that many failed S1 trades had a low volume participation percentage or occurred when a higher-timeframe trend was against the trade. Similarly, analyze trades’ exit reasons – e.g., if a large fraction of losses hit the stop-loss versus trailing out at break-even, that tells you something about initial stop placement or timing.

Examine Missed Opportunities: If the logging (with improvements discussed below) shows signals that were generated but not traded due to filters (e.g. already in a position, or daily loss limit hit), include those in analysis. You may observe, for instance, that a lot of skipped signals would have been profitable – indicating your one-at-a-time asset rule might be too conservative – or vice versa.

c. Derive Insights and Hypotheses: From the above analysis, formulate hypotheses for strategy improvement. For example, you might conclude: “Trades where the BB width percentile was below 10% have a poor win rate – perhaps require a minimum volatility threshold for S1 setups.” Or: “Long trades taken against a negative bias (as indicated by a negative bias_score) mostly failed – maybe filter those out.” The key is linking outcomes back to the logged inputs/decisions. The structured reasons (why_items) logged for each signal are extremely useful here – by scanning the reasons listed for losing trades, you get human-readable insight into what the strategy saw. Perhaps many losing trades had a reason code indicating “trend strength: weak” – suggesting that adding a trend filter could help.

d. Iterate and Refine: Feed these insights back into strategy modifications. This could mean adjusting parameters (e.g. require higher participation or break_quality scores to take a trade), adding new filters (e.g. skip trades when a certain condition in conditions_met is false), or tweaking exit rules (if logs show many trades giving back profit, maybe introduce a tighter trail stop). Because the system is designed for repeatable runs, you can implement a change, then quickly run a new backtest/paper run and use the logging to verify if the metrics improved. For example, if you tightened a condition, you would look in the next run’s logs to see if the problematic trades are fewer (and check overall profitability hasn’t suffered elsewhere).

e. Ongoing Monitoring: In a live or paper-trading setting, use the logs after each batch of trades (say daily or weekly) to do quick post-mortems. Identify that day’s worst trade and drill into its log details: was it executed as expected? Did any logged warning (e.g. a circuit breaker trigger or an unexpected exit reason) occur? The system logs events like daily loss circuit-breakers being hit, which should prompt strategy or risk limit adjustments. In summary, treat the logging system as your “black box flight recorder”: after each flight (trading session), review it to understand performance and adjust the strategy’s knobs accordingly.

By following this workflow – Log → Analyze → Identify weaknesses → Adjust strategy → Repeat – the team can systematically improve the algorithms. The key is that the rich, structured log data provides concrete evidence for what’s working or not, enabling data-driven refinement instead of guesswork.

3. Planned Logging Enhancements and Implementation Details

To further strengthen the feedback loop, we propose several concrete logging improvements. These will ensure no critical data is missing for post-trade analysis and make it easier for developers to use the logs for learning. Below is the plan, including what to log, where in the code, and in what format:

(a) Log Full State Snapshot for Each Trade: We should capture a more complete set of indicator values and strategy state at the moment of entry, beyond the few currently stored, so that analysts can use all relevant features in regression analysis. Currently, when converting a signal to a trade, the code logs a limited subset of fields (entry/stop price and r_value) and the score components/state. We will extend this:

Implementation: In RunExecutor._signal_to_trade (responsible for SCAN/PAPER trades) and in the backtest pipeline when creating pending_entries (in _execute_backtest), include the entire state dict from the signal’s payload as the state_snapshot. For example, for S1 signals we can include fields like bias_score, squeeze_on, etc., which are already available in signal.payload["state"]. For S2, include converging, ma_gap_atr, etc. This essentially means populating trace.state_snapshot with a clone of signal.payload["state"]. In the backtest code, we will carry the evaluator state through – e.g., add a field state_snapshot to the pending_entries dict (containing the S1State or S2State as a serializable dict) when a setup fires. Then, modify RunExecutor._position_to_trade to include that in the TradeTrace. This way, when we later query run_trades.trace_json, we’ll see a full snapshot of the market state (e.g. “bb_width_pctile”: 22, “squeeze_age”: 5, “bias_score”: -1.2, etc.) at entry. The format will remain JSON (as part of trace_json), so it’s easy to parse.

Rationale: Having this full feature vector per trade enables richer analysis. For instance, one could use these snapshots to train a model to predict trade outcomes or to find patterns (maybe some combination of features leads to failure). Currently, much of this data is already being logged for signals, but this change ensures it’s directly tied to each trade for one-stop analysis.

(b) Include Reason Codes with Trade Logs: The system logs human-readable reason strings for signals (the why_items list) in the signal events, but these weren’t explicitly carried into the trade records for backtests. We will make sure each trade log also includes the top reason codes explaining why the trade was taken.

Implementation: In RunExecutor._signal_to_trade, we already attach why_items to the trace (in fact, the code ensures at least 3 reasons are present) for scan trades. We will ensure this is done uniformly: e.g., for backtest trades, when creating a pending_entries from a signal, store why_items (from signal.explain) in that entry. Then in _position_to_trade, if available, attach those to trace. One convenient approach is to put why_items into the conditions_met or state_snapshot of the position’s trace. For example, we could set pos["conditions_met"]["why_items"] = [...] before closing the trade. Alternatively, simply include it in state_snapshot (as is done for scan/paper trades) – e.g., trace.state_snapshot["why_items"] = [...]. This will be stored as a JSON array in the trace_json column. No new columns are needed; we’re utilizing the existing JSON structure.

Rationale: Including the “why” explanations per trade greatly helps the post-mortem process – a developer can read the primary reasons a trade was initiated (e.g. “BB squeeze ON for 5 bars; Volume participation: 60%; Break quality: 80%”). This makes it easier to interpret the numeric features and pinpoint which reasoning frequently coincides with bad outcomes. It bridges the gap between raw data and human intuition during analysis.

(c) Log Skipped Signals/Trades and Filter Conditions: In order to learn not just from executed trades but also from opportunities the strategy passed up, we’ll add logging for cases where a signal was dropped due to strategy constraints. For example, in backtests we currently continue without logging if: a) the max number of concurrent positions is reached, b) the asset already has an open position (one_per_asset rule), or c) the daily loss limit (circuit breaker) is tripped. We propose:

Implementation: Introduce logging in _execute_backtest and PaperTradingEngine.process_signal for these skip scenarios. This could be at DEBUG level for per-signal granularity or at INFO with aggregation. Specifically, in the backtest loop where we skip adding pending_entries:

After the loop, if any skips occurred, log an INFO RunEvent summarizing: e.g. “Skipped 3 signals due to one-per-asset rule and 2 signals due to max position limit.” This can be done by maintaining counters for each reason, then using repo.add_event(...) at the end of the run.

Additionally (or alternatively), add a logger.debug within the loop for each skip, e.g.: logger.debug("Skip signal on %s: already holding position in asset", symbol). Because the structured logger is in use, we can include context like {"event": "signal_skipped", "reason": "one_per_asset", "symbol": symbol} in the extra fields.

For the daily loss limit, we already log when the circuit breaker triggers in paper trading; we should do something similar in backtest. E.g., if daily_pnl drops below –max_daily_loss, log a warning event (and optionally stop taking new entries for that day in simulation). This way, the post-run analysis can see if the loss limit was hit and how often.

Rationale: Logging skipped trades gives insight into whether strategy constraints are too tight or just right. If analysis shows that many high-scoring signals are being skipped (and if we simulate what their outcome would have been or observe them in live), we might decide to relax a constraint (or confirm that skipping protected us). This data prevents “silent” opportunity loss from being overlooked in the learning process.

(d) Correlate Signals to Trades via Run ID: To support end-to-end analysis, it helps to tie the signal generation logs with the eventual trade outcome by a common identifier. We will ensure that whenever a log_signal_event is recorded, it is linked to the active run (if any).

Implementation: The log_signal_event function already accepts an optional run_id, but in the current code the calls from signal_engine do not pass it (since scanning is often run outside the context of a run). We can modify the run execution logic to supply a run_id when appropriate. For example, in RunExecutor._execute_scan, after initializing the SignalEngine, set a context variable or pass the run_id into the engine so that inside evaluate_setups it can include that run_id in log_signal_event. A simpler approach is wrapping the engine.scan() call: for runs, we could intercept the signals and manually log events with run_id. However, the cleaner way is to extend log_signal_event(..., run_id) usage. We’ll update the evaluate_setups calls and to include run_id if available (this might involve making run_id accessible in SignalEngine, perhaps via a global context var similar to ctx_run_id).

Rationale: With run IDs on signal events, one can filter the signal_events table by a specific backtest or paper-trading run, and directly compare all signals generated vs. trades taken vs. trades won. This is useful for evaluating strategy sensitivity: e.g., “In run 1234, 100 signals fired but only 10 trades were taken – was our selection too strict?” It also helps in cases where we want to analyze false positives (signals that looked good but we chose not to trade) or false negatives (missed signals). Note: We will be cautious to use this in moderation for backtests – logging every signal in a 1000-trade backtest could be heavy. We might enable full signal logging with run_id in smaller-scale runs or have it toggle-able. For live/paper trading (where volume is lower), always logging with run_id is highly beneficial.

(e) Unified Format and Additional Fields: We will keep all new logs in the same structured JSON format for consistency. Any new fields (like a reason for skip, or an added indicator in state_snapshot) will simply appear as new keys in the JSON objects – no breaking changes. For persistent storage, the existing JSON columns (trace_json, payload_json in events) will accommodate the extra data. For example, after these changes a trade’s trace_json might look like:

{
  "conditions_met": {"setup_triggered": true}, 
  "entry_reason": "S1_TRIGGER",
  "indicator_values": {"bb_width_pctile": 22.5, "squeeze_age": 5, "clv": -0.3, "volume_z": 1.4, ...},
  "state_snapshot": {"bias_score": -1.2, "squeeze_on": true, "why_items": ["Low volatility squeeze", "Moderate volume participation", "..."], ...},
  "score_components": {"severity": 0.8, "bias_strength": 0.5, ...},
  "exit_reason": "STOP_LOSS",
  "exit_explanation": "Exit at -1.0R after 3 bars"
}


This is an illustration combining various pieces we plan to log. The format is line-delimited JSON in logs and JSON fields in the DB, which is already the case, so existing tooling (e.g., consuming logs with Elastic/Kibana or querying Postgres JSON) will continue to work. We will ensure that any new data (bias_score, etc.) is logged with clear keys and that numerical values are rounded or formatted consistently (as done elsewhere in logging).

By implementing these improvements, developers and strategists will have a complete picture for each trade: all the inputs (indicators, state, and even textual rationale), the decision taken (or skipped), and the final outcome. The code locations to be touched include: Backend/worker/app/run_executor.py (in _execute_backtest for skip logs and adding state to entries, in _signal_to_trade and _position_to_trade for trace enhancements), Backend/worker/app/signal_engine.py (to pass run_id to log_signal_event), and Backend/worker/app/paper_trading.py (for any skip/circuit-breaker logging not already covered). These changes are straightforward to implement as they mostly involve adding fields to existing log calls or data structures, rather than altering logic.

Once in place, the fast iteration loop will be fully supported by logging: one can run a simulation or live paper test, immediately pull rich data on every signal and trade, and pinpoint exactly how to adjust the strategy. Developers can proceed to code these logging additions, and analysts can then plug the new data into their notebooks or dashboards to accelerate the strategy improvement cycle.
